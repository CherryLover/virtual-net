## 2. 产品定位与统一概念

目标：让用户搭建网络，检查某次访问是否成功，看到实际路径、阻断位置和原因。不测真实设备，不承诺真实网速或现实网络的可达性。

| 概念 | 含义与边界 |
| --- | --- |
| 网络区域 | 办公网、访客网、云网络、外部网络等可命名分组；不直接决定放行或拒绝 |
| 网关 | 承担路由、地址转换或流量转发的设备；角色由配置与连接决定，不按软硬件或产品命名 |
| 访问控制 | 按规则放行、拒绝或处理访问；可表现为独立设备，也可能是主机上的能力 |
| 服务器 | 有地址、端口与服务的主机；不限定云厂商或部署方式 |
| 代理 | 可单独添加的实体，接受客户端连接，再向目标建立连接 |
| DNS 服务 | 负责解析、转发或按规则改写应答的服务 |
| 虚拟化主机 | 容纳虚拟设备、网桥和网卡；具体产品只用于可选示例 |
| 目标服务 | 用户想访问的服务，包含域名、地址、端口等信息；不等同于某个固定网站名单 |

默认文案采用“访问控制”“受限目标”“规则拒绝”“DNS 应答改写”“网关”“虚拟化主机”。具体地域、产品或真实站点可出现在明确标注的示例中，但不内置为全局判断依据。诊断可以准确说明“被防火墙规则拒绝”，不需要隐藏实际原因。

区分三个层次：设备与连线决定路径，规则与服务决定行为，画布位置与区带负责展示。不得通过移动节点或改变线形，悄悄改变模拟结果。

## 3. 访问控制与 DNS 的调整

### 需要替换的旧假设

| 旧方案假设 | 新方向 |
| --- | --- |
| 全图只取第一台启用的边界设备 | 按实际经过的设备逐台执行规则；支持多层访问控制，不设全局唯一边界 |
| 按国内、境外决定是否过滤 | 按来源、目标、协议、端口等规则匹配；区域可作为可选条件，不自带阻断含义 |
| 未知区域直接放行 | 无命中规则时遵循明确默认动作；地址未知与访问被拒绝分别解释 |
| 只有 IP、域名黑名单 | 支持允许与拒绝、规则顺序和默认动作；高级匹配分阶段实现 |
| 只要图中有边界设备，DNS 就可能被改写 | DNS 服务自身应答策略与查询路径上的干预分开；不受未经过的无关设备影响 |
| 改写答案必然连接失败 | 可以失败，也可以连接另一服务或提示页；同时显示原目标与实际解析结果 |
| 图中有代理就不再警告 | 必须确认这次请求使用了代理，且代理入口与出口路径都可用 |
| 某类协议必然被封、另一类必然通过 | 结果由当前规则和可观察信息决定；“有识别风险”不能伪装成确定性模拟结论 |

### 实施前必须定清

- 规则采用首条匹配还是其他优先级方式；默认动作；拒绝是丢弃还是显式拒绝。
- 入站、出站、转发和返回连接如何检查；已建立连接是否自动允许返回。
- 主机自身访问规则与路径上的访问控制是否共用规则表达，以及执行顺序。
- 域名精确匹配、子域名、通配符的范围；IP 是否支持网段。
- 域名、加密握手信息、应用内容哪些对当前设备可见；不能让设备读取本来不可见的信息。
- DNS 本地解析、上游转发、代理端解析各走什么路径；缓存和加密 DNS 的首期范围。
- 目标库允许多个域名共用 IP，以及一个域名有多个地址的时间点；旧方案“IP 全局唯一”不宜成为长期约束。

## 4. “代理”实体

### 用户可见的体验

左侧设备库中有独立的“代理”入口，可搜索、点击添加或拖入画布。加入后是能选中、命名、连线、配置、删除的节点，具有自己的连接状态和诊断结果。它不是示意图标，也不是自动生效的全网开关。

建议左侧按“终端与服务器”“网络设备”“服务与代理”分组，代理放入后者；分组名称与顺序待视觉方案确认。不要仅新增一个空白“服务器”类型后要求用户自行猜测如何开启代理。

### 配置建议

| 配置组 | 内容 |
| --- | --- |
| 网络连接 | 地址、掩码、网关、DNS、接线端口；与普通主机复用能力 |
| 代理入口 | HTTP / SOCKS5 等协议、监听地址、监听端口、启停状态 |
| 身份验证 | 无认证或测试账号密码；明确只填写模拟凭据，不收集真实密码 |
| 目标解析 | 客户端已解析后传 IP，或将域名交给代理解析；按协议能力限制 |
| 出口 | 直连目标或使用上一级代理；后者可后续实现，但应预留链路表达 |
| 访问范围 | 可访问的目标与端口、连接来源限制；与通用访问规则衔接 |

“IP 代理”不作为独立协议：IP 与端口表示入口地址，实际行为由 HTTP、SOCKS 等协议决定。IP 池与轮换没有在本轮确认，不纳入首批要求。

### 协议与行为边界

- 建议首批覆盖 HTTP 正向代理、HTTP CONNECT 与 SOCKS5 的 TCP 连接；UDP、中转链和网络隧道单独排期，待确认。
- CONNECT 不等于客户端到代理的传输一定加密；SOCKS5 本身也不提供加密。协议、传输保护和出口分别表达。
- 显式代理的应用请求与普通网络测试分开。配置应用代理，不得让普通 ping 自动走代理。
- 客户端必须明确如何选用该代理：单次访问选择、设备级设置、规则选择的优先级待定。
- 完整过程至少区分“客户端到代理”“代理身份验证”“代理解析目标”“代理到目标”“返回结果”。每段产生可定位的原因。
- 代理与网络隧道不是同一回事；代理通常建立另一段连接，不要全部伪装为原始 IP 包的简单封装。
- 失败后是否退回直连必须是显式策略，不能默默改变访问路径。

### 内部表示建议

建议“代理”是复用主机网络能力、内置代理服务的专用节点，避免复制一套地址分配和路由逻辑。是否采用专用设备类型，或“服务器 + 代理服务”的组合表示，由实施前设计确定；无论内部怎么表示，左侧都必须保留独立代理入口。

## 5. 页面布局与交互

### 设计方向

采用工作台式网络编辑器：信息密度适中、操作分组明确、选中状态清楚。保留中间无额外装饰框的主画布，不改成首页、仪表盘或卡片堆叠，不用大面积装饰挤占操作空间。

建议延续现有浅色中性底色与状态色语义，重新统一间距、字号层级、图标与表单样式。具体色值、字体、尺寸和高保真稿待讨论，不把“更现代”理解为只换主题色。

### 顶部工具栏

- 文件操作（新建、导入、导出、示例）与编辑操作（撤销、重做）分组；验证保留醒目的直接入口。
- 保存状态清楚但不抢占空间；长网络名称不挤压其他按钮。
- 常见工具使用标准图标与悬停提示；明确命令允许图标加文字。沿用已有图标体系或统一引入图标库，不混用字符图标。
- 次要操作收纳到菜单；窄屏折叠而不是横向溢出。

### 左侧设备库

- 支持分组、搜索与收起，保留点击添加和拖拽添加的便捷方式。
- 代理与其他设备使用一致的图标、尺寸、选中和拖拽反馈。
- 当前未实现的设备不能伪装成可用入口；说明范围放在文档或明确的未开放状态中。

### 中间主画布

- 保留平移、缩放、框选、批量移动、节点配置、路径播放的工作方式。
- 改进选中与悬停反馈、工具命中区域、端口与连线标签；不随便改已有手势。
- 两侧面板收起或展开后，画布保持合理可用面积，不强制重置用户视角。
- 现有 240px 左栏与 320px 右栏只是实现现状，不作为新设计的固定要求。

### 右侧节点操作面板

- 顶部稳定显示设备名称、类型、状态和关闭入口；配置区域独立滚动。
- 建议按“配置 / 端口 / 验证”组织；不同设备显示适用分组，避免无内容标签页。
- 常用配置优先，高级项渐进展开；开关、选项、数值分别使用合适控件。
- 错误紧邻字段，点击诊断结果能打开对应分组并滚动定位，不被折叠项隐藏。
- 区分输入中的临时内容与已生效配置，避免半个 IP 触发全图反复报错；采用失焦提交还是显式应用需统一决定。
- 切换节点时不串用上一个节点的输入；未提交内容的处理必须明确。
- 单节点、多选、连线、未选中各有对应内容；配置与验证结果之间能方便往返，不能只能点空白处才找回结果。
- 删除、恢复默认等破坏性操作与常用操作分开；保持撤销能力。
- 桌面优先保证高效操作；小窗口采用可收起面板，手机采用单面板切换或抽屉的具体方案待定。

## 6. 连线与端口

### 现状核实

- `apps/web/src/canvas/DeviceEdge.tsx` 已使用自动贝塞尔曲线，缺少手动调整，不需要从直线升级。
- `SwitchNode.tsx` 在端口数小于 17 时全部放底部，17 个及以上才分上下两排。
- `PortHandles.tsx` 同一端口的 source / target 柄表示拖线方向，不表示两个独立物理端口。
- 路径动画当前沿实际 SVG 连线取点；新增线形必须保留这一契约。

### 曲线拖拽要求

- 选中连线后出现可拖拽控制柄，调整贝塞尔曲线以手动避开节点和标签；未选中时不铺满控制点。
- 默认仍自动生成合理曲线；提供“恢复自动线形”。本轮不承诺全自动避障。
- 控制柄、连线、节点拖动、画布平移的命中与手势不冲突；一次拖动完成对应一次撤销。
- 线形调整后标签位置仍合理，动画沿新曲线往返，错误与选中高亮覆盖同一路径。
- 缩放、平移、节点移动后曲线不跳变；节点移动时控制点如何跟随需定清。
- 手动线形属于展示数据：应保存、导出、导入、撤销与重做，但不改变连接关系或让验证结果过期。
- 老文件没有线形数据时使用自动曲线；删除连线后清理相应展示数据。

建议先采用三次贝塞尔曲线的两个控制柄；是否改为拖线身、折点或多段曲线，先通过小原型比较，不在本轮强制定稿。坐标建议相对端点保存，最终方案需覆盖单节点与双节点移动行为。

### 上下端口与同级连接要求

- 普通交换机也应能从上侧和下侧方便接线，不再依赖“端口超过 16 个”才开放上侧。
- 展示位置不改变端口身份、VLAN、占用情况和连接语义；一个物理端口仍最多连接一根线。
- 同级设备连接应尽量从合理方向出线，避免被强制从底部大幅绕行；是否开放左右侧作为后续方案选项。
- 端口名称、连接状态、VLAN 信息应可识别；高端口数时避免节点无限变宽和标签重叠。
- 已有连线迁移后端点仍指向原端口，不得为换边删除重建物理端口。

待比较两种方案：端口可选择显示在哪一侧，或同一逻辑端口提供上下两个视觉入口。建议优先前者，避免用户误以为端口数量翻倍；若采用后者，必须同步占用反馈并保证视觉柄 ID 与逻辑端口 ID 的映射不混淆。

## 7. 技术边界与兼容要求

- 展示配置应与模拟配置分离。当前 `store/topology.ts` 的结构指纹包含完整 ports 与 links，新增线形或端口展示字段后必须调整指纹，不能只口头声明“不影响验证”。
- 数据结构、导入校验、自动保存、历史记录、画布映射与动画需一起检查，不能只改 Edge 或节点组件。
- 先确定新数据格式的兼容方式；新增字段不意味着旧版本程序也能读。需要说明新程序读取旧文件与旧程序读取新文件各自行为。
- 代理路径需要表达多个相关连接，不能只在现有结果里多插一条文字。验证状态与逐跳解释如何关联各段连接需先设计。
- 不把当前透明访问控制节点直接称为所有形态的通用防火墙；透明、路由型、主机规则是否首期全做需明确。
- 本轮不新增后端、真实代理连接、真实流量转发、账号系统或部署任务。

## 8. 建议实施顺序与待定清单
