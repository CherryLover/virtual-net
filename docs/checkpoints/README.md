# 检查点文档规范

`docs/checkpoints/` 下每个检查点一份文档，是开发时的**指引**：说明具体做什么、做到什么程度算完成。
`docs/TEST-PLAN.md` 是独立的**测试表**：从上到下逐条检查每个功能该怎么验证。两边通过编号互相引用。

总纲在 [../../ROADMAP.md](../../ROADMAP.md)。文档范围不能超出总纲，发现总纲缺东西写进「待定问题」，不要自行扩范围。

> 2026-09-07：后续阶段先读 [方向与页面优化](../design/network-model-and-ui.md)。本文件下方 CP4 特定设备术语仅为旧文档对照，不作为新模型命名依据。CP4 旧细化文档待重写，CP5–CP7 及 UX 需先细化；CP0–CP3 历史约定中受新展示模型影响的部分须显式列出迁移，不静默覆盖。

## 编号

- 步骤：`CPx-Sn`，如 `CP1-S3`。一个步骤是一个可独立完成、可独立验收的工作单元
- 测试用例：`T-CPx-nnn`，如 `T-CP1-004`。只在测试表里分配，检查点文档回填引用
- 引用方式：相对路径链接到文件，链接文字里带编号。例：`[CP1-S3](CP1-lan-basics.md)`、`[T-CP1-004](../TEST-PLAN.md)`。不依赖标题锚点

## 文档模板

```markdown
# CPx 检查点名称

> 总纲对应章节：[ROADMAP.md](../../ROADMAP.md) 的「CPx」
> 前置：需要先完成哪些检查点
> 状态：未开始 / 进行中 / 已完成

## 目标
一段话。做完这个检查点，用户能看到什么、能做什么。

## 范围
### 做
### 不做（明确排除，避免开发时顺手加）

## 关键设计
这个检查点引入或改变的数据结构、引擎行为、界面布局。要具体到能直接开工：字段有哪些、算法按什么顺序判断、界面分几块各放什么。
可以给小段 JSON 或类型示例说明结构，不写实现代码。

## 步骤

### CPx-S1 步骤名
- **做什么**：一两句
- **怎么做**：要点列表，具体到模块、文件、界面元素
- **产出物**：新增或修改的模块、界面、文档
- **验收标准**：每条是「操作 → 预期结果」。标明验收方式：【引擎测试】引擎包自动测试 /【网页测试】网页包纯函数自动测试（CP3 起）/【页面操作】手动点 /【命令】终端跑
- **测试用例**：待回填

### CPx-S2 ...

## 阶段完成标准
把总纲里的验收场景展开成可照着操作的步骤：从哪开始、点什么、填什么、看到什么才算过。

## 对其他检查点的约定
本检查点定下的、后续检查点必须遵守的东西。例：数据结构字段、端口命名、引擎接口。

## 待定问题
写文档时发现但没法在本检查点内定的事。

## 关联文档
- 上一个 / 下一个检查点
- 测试表
```

## 验收标准的写法

- 每条都能被一个人照着做出来，不需要看代码
- 写清楚前提、操作、预期。反例：「ping 能通」。正例：「电脑 A 设 192.168.1.10/24 网关 192.168.1.1，路由器 lan1 设 192.168.1.1/24，A 与 lan1 连线。在 A 上 ping 192.168.1.1 → 结果面板显示"通"，路径显示 A → 路由器 → A」
- 失败场景要写失败原因的预期文案要点，不只写"不通"
- 引擎能覆盖的必须有【引擎测试】；网页侧不依赖 React 的纯逻辑用【网页测试】；界面才能验证的用【页面操作】

## 术语与命名（所有文档统一）

设备类型与内部标识：

| 中文名 | 内部类型 | 端口命名 | 引入 |
| --- | --- | --- | --- |
| 电脑 | `pc` | `eth0` | CP1 |
| 路由器 | `router` | `wan`、`lan1`…`lan4` | CP1 |
| 互联网 | `internet` | `port1`…`portN`（按需增加） | CP1 |
| 交换机 | `switch` | `port1`…`portN`，默认 8 口 | CP2 |
| 无线 AP | `ap` | `uplink`、`wlan1`…`wlanN`（无线客户端视为连到 `wlanN` 的有线口，始终多留一个空闲口） | CP2 |
| 光猫 | `modem` | `wan`（上行，连互联网）、`lan1`（连路由器 WAN） | CP2 |
| 长城防火墙 | `gfw` | `inside`（朝内网）、`outside`（朝互联网），二层透明 | CP4 |

通用词：
- **连线**：两个端口之间的一根网线，`link`
- **拓扑文件**：整张图导出的 JSON，`topology`
- **决策记录**：引擎每处理一跳产生的一条说明，`decision`。CP1 定义结构，CP3 用它做动画和解释
- **静态检查**：不跑模拟、只看配置就能发现的问题，`lint`
- **验证**：在页面上发起 ping / 访问网站 / DNS 查询 等动作，`probe`
- **结果面板**：页面右侧或底部显示验证结果与静态检查结果的区域

界面三块固定叫法：**左侧设备栏**、**中间画布**、**右侧面板**（配置与结果共用，按选中状态切换）。

## 与测试表的关系

1. 先写检查点文档，把每个步骤的验收标准写清楚
2. 再写 `docs/TEST-PLAN.md`，把验收标准逐条整理成测试用例并编号
3. 回到检查点文档，把每个步骤的「测试用例」从「待回填」改成对应编号的链接
